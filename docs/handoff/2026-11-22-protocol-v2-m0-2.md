# 协议 V2 · M0 第二部分

**传输接口保留候选状态。**默认 H2 ClientHello 在 50 次采样中均与 Chrome 157 有差异。显式参考配置匹配，两条调用路径分别记录。默认 H2 UDP、Android 绑定与高延迟切换已实测。

## 实现与边界

- H2 UDP 的 authority 为目标 host:port。绑定设备以后才解释单个 `Nexus-Flow: udp` 与 `Capsule-Protocol: ?1`；未认证的请求继续到 Caddy 文件站点。H3 沿用 RFC 9298。服务端无需重新执行；Go job、AAR、Android 和 systemd 均已去除历史开关。
- Config.Protect 由 TCP dialer 和 UDP listener 在 connect/bind 前执行，覆盖首次连接、备用连接和回切探测；返回 false 以码 1 中止。Java 的 Protector 接收 int fd，Mobile.errorCode 接受原始异常。乐观首段收到正式拒绝时映射状态码；没有最终响应时才返回 7。节点及健康请求省略库的默认 User-Agent。
- QUIC 客户端与节点目的拨号按已核验的地址依次尝试，按剩余地址分配截止时间。服务端先检查完整 DNS 回答，混入禁止地址仍整体拒绝。UDP 在内核接受 connect 后无法据此判定远端是否响应。H2 推测性预建至少相隔 10 秒；已经确认连接断开的恢复拨号可以另行启动。
- 节点 QUIC 初始流/连接窗口从 2 MiB / 3 MiB 改为 512 KiB / 768 KiB，上限保持默认值。原版 quic-go 和 apernet 首次发送控制器的构造参数均是 Reno，完成设备认证后才更换 BBR。两份 `internal/protocol/params.go` 的第 19、22 行给出初值；`internal/ackhandler/sent_packet_handler.go` 分别在第 137、181 行选择 Reno。[上游](https://github.com/quic-go/quic-go/tree/v0.63.0/internal) · [apernet](https://github.com/apernet/quic-go/tree/2895f039137a/internal)
- 开发分支改动位于 `v2/transport`、`mobile`、`server`、`udp`、节点入口与 systemd 单元、Caddy 补丁、集成夹具、AAR 构建脚本、Android Application / M0Check、CI 和传输 API 文档。规范分支更新承载表、错误码、互通向量、已知短板、逐笔 CSV 和索引。

## 复现

先按开发分支 `docs/protocol/v2-transport-api.md` 在仓库外生成 modfile 和节点。在 v2 模块内用相同 GOFLAGS 编译 `integration/testdata/gate.go`，它调用正式 transport；server 子命令生成临时 Caddy JSON 后运行 LAB_NODE。实验仅使用即时生成的合成 P-256 身份。WSL 每格使用独立网络命名空间。多个实验共用宿主 CPU，各自具有独立的流量整形链路。

- 配对吞吐和 UDP 的入口为 `integration/testdata/gates.py`。设置 PYTHONPATH 为规范分支 tools，LAB_NODE 指向已构建节点。例：`unshare -n python3 integration/testdata/gates.py "$GATE" "$HYSTERIA_DIR" "$OUT" --loss 5 --pairs 20`。UDP 改用 `--udp datagram` 或 `--udp capsule`，每格开始时重置相同的 netem 种子。每次 bulk 经固定内容的 SHA-256 校验。每个配对编号先测 Nexus、再测 Hysteria。bootstrap 按同一编号有放回重采样 10,000 次（随机种子 4），以基准总体中位数为分母；失败保留在原始记录。
- 故障与误切复用试验分支 `spikes/go-v2/recovery.py`，参数为正式 gate、受信参考 profile、both / mid / normal / idle、输出路径、`--rtt 300 --jitter 20 --count 100`。采集 ClientHello 复用 `spikes/go-utls/samples.py` 和规范分支 `tools/benchmark_v2_handshake.py:describe`，只保存解析字段。未提交抓包、身份、原始 ClientHello 或产物。

## 未覆盖及冻结条件

默认 H2 配置使用固定版本的 uTLS 预设，实验室的显式参考 profile 没有作为默认配置随客户端发布。冻结前需确定受信 profile 的发布与维护方式，重新验证缺省路径。Android 的回调实测检查调用与拒绝传播；本轮没有在真机或全设备 VPN 下验证物理路由。arm64、StrongBox、Windows 节点运行、跨运营商网络、断路紧随前一次废弃预建的最坏时延、云端 CI 均未验收。UDP 抖动每格只跑了一次。

**冻结前必须完成：**
1. **默认 H2 握手要改成内置的 Chrome 157 参考配置。** 现在缺省走 uTLS 预设，50/50 都不匹配（缺 ca34 和 0904/0905/0906）；只有显式传入参考配置才是 50/50。建议把已核验的配置随客户端一起发布，形式二选一：
   - 去掉 SNI、随机数和密钥份额后的字节文件，用 go:embed 嵌入；
   - 或等价的 Go spec。

   同时提交生成脚本，并加一个单元测试，确认默认路径的 JA4 和扩展集合与参考一致。还要写明 Chrome 稳定版更新后的流程：重新采样 → 跑 50 次比对 → 更新配置。H3 依赖分支里的 ChromeParrot，也按同一流程跟踪。
2. **Android 上节点域名的解析没有被保护。** protect 只覆盖我们自己的套接字，管不到系统 getaddrinfo 发出的 DNS 查询。VPN 运行时，解析节点域名可能绕回 TUN，或者走错网络。文档建议 Java 侧传入解析好的 Endpoint，但 Endpoint 只能写一个地址，IPv4 / IPv6 回退就没了。建议在 Config 和 `Mobile.start` 里增加可选的 `Resolve(host) → 地址列表` 回调，Java 侧用底层 Network.getAllByName 实现。不传时沿用系统解析。

**统计口径要固定（不阻塞本轮）。** 5% 丢包这一格，第一批 20 对没过，用新种子再跑 60 对才过。这次复核是事先声明的、种子独立、结果没有合并，而且两批的点估计一致（−1.7% 和 −1.5%），所以我接受这个结论。但「没过就再测」不能变成惯例。另外，如果改用配对差的中位数，第一批的下界是 −4.61%，也能过；口径一换结论就变，说明规范必须写死。以后每格固定 60 对，统计量写死为现在这种更保守的「两组中位数之差 ÷ 竞品中位数」，写进规范第 7 节。

**值得查的性能线索（不阻塞）。** 0% 丢包时比 Hysteria 稳定慢 1.1%，区间只有 [−1.16%, −1.04%]，说明是系统性的差距。怀疑服务端 `flushingWriter` 每次写入都 flush，导致数据包没有装满。可以试试改成只在读端空闲时 flush，或者用更大的缓冲，复测这一格。

**UDP 默认值：同意默认用 capsule。** Hysteria 只宣告 QUIC 0x20、不宣告 H3 51，所以我们开启原生 DATAGRAM 后反而比 Hysteria 更容易被认出来。默认关闭是正确的，需要实时 UDP 的节点再手动开启。
