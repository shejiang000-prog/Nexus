# Android 2.0.0 本地发布演练

开发基线 `548f3fe`，规范基线 `5afa7ad`。客户端版本码从 10001 升至 20000，正式包名为 `dev.nexus.android`，正式签名仍使用原工作流的密钥配置。本次两个 Release APK 均用本地 Android 测试证书签名。

## 包内容与配对

| APK | 架构 | 字节 | MiB |
|---|---|---:|---:|
| Nexus-2.0.0-arm64.apk | arm64-v8a | 25,848,158 | 24.65 |
| Nexus-2.0.0-universal.apk | arm64-v8a、x86_64 | 51,135,415 | 48.77 |

- 在 Windows 上离线执行 `:app:assembleRelease`，使用锁定源码生成的双架构 V2 + libXray AAR 和常规 Release 的 R8 配置。两个 APK 均通过 `apksigner verify`。核实包名、版本、ABI 和非调试标志，演练包签名与本地 1.0.1 演练包相同。
- `prepare_android_release.py v2.0.0` 配对通过。APK 中的两个 SHA-256 分别匹配独立的 amd64、arm64 Linux ELF，出包目录中的资产也与 `SHA256SUMS.txt` 一致。节点程序、V1 脚本和 V1 指纹文件均未进入 APK。
- 检查两个 APK 的清单、DEX 和原生导出。清单无 instrumentation，DEX 不含验收 runner、传输追踪、实验室计数器或分流测试夹具。共享原生库只导出用于分流的 `Tunnel.split`。V2、第三方订阅所需的 Xray、分流和兼容库继续随包分发。
- Release 包产物位于演练机仓库外的 `E:/temp/nexus-v2.0.0-rehearsal/assets/`。其中的测试签名 APK 仅供演练。正式签名、打标签、推送、合并和发布留待用户确认。

## 客户端变更

移除 V1 私人节点连接、配置导入、部署、绑定、邀请和本地端口转发。升级清理本机 V1 配置、设备身份、旧 SSH 绑定、私有节点设置和恢复连接请求，保留 V2 与第三方订阅使用的数据和密钥。独立历史 Rust CLI 和桌面原型不属于此次 Android 发布资产。

「设置 → 更多 → 导出诊断信息」用系统分享面板提供文字摘要，只有点击才生成。字段为版本、可识别的公开机型、网络类型、最近一次 H3/H2 切换及恢复的 UTC 时间和最近的 V2 错误码。机型不能安全识别时显示「未识别」。Release 单元测试覆盖正常字段并注入十类敏感样例，1/1 通过。

## 覆盖升级与分享面板

在空白雷电实例 1 安装本地测试签名的 1.0.1 Release，预置合成 V1 配置、管理绑定、设备密钥和加密第三方订阅。用同测试证书签名的 2.0.0 universal APK 执行一次 `adb install -r`。首次打开后，旧配置、绑定与 V1 密钥均已清除，原订阅仍能解密并在首页显示，原有路由偏好也得到保留。两个版本均使用 `dev.nexus.android`。合成条目采用 1.0.1 的实际加密格式，节点样例缺少引擎所需的 `config` 字段，因此本次验证了订阅数据保留与解密。订阅解析与 Xray 出站转换代码相对基线无变更，此次没有用该条目实连。

在升级后的 Release 设置页实际点击「导出诊断信息」，Android 分享面板显示 2.0.0、Android 14、网络类型和当前诊断摘要。没有选择接收方或发送。首次读取升级状态时验收进程附加超时，重新打开该进程后取证成功，APK 只覆盖安装一次。临时实例已删除，原雷电实例 0 保留原有安装和数据并已关闭。

## 实测依据

发布说明沿用 M4 单线路的三个样本。UDP 在使用中被封锁后，新 TCP 回声为 3.62–4.43 秒，VPS-B 网页主文档收齐为 4.98–6.34 秒，网页的 5 秒门槛未全部达到。本轮未复测公网或用户手机。详见[上轮评审和真机检查](2026-11-25-m4-2-public.md)。

- 本轮没有修改 Go 代码。用 `nexus-m42-dns.aar` 离线执行 `assembleDebug testDebugUnitTest testReleaseUnitTest`。为了只跑测试，跳过了 `requireReleaseSigning`。构建成功，Debug 与 Release 各 6/6 通过，其中包括 `DiagnosticExportTest`。
- `test_android_release_assets.py` 通过。`test_android_release_download.py` 需要 `sh`，在 Windows 上跳过。
- 检查演练资产 `E:/temp/nexus-v2.0.0-rehearsal/assets`：
  - `SHA256SUMS.txt` 中的条目全部通过校验。
  - 两个 APK 的包名均为 `dev.nexus.android`，版本 2.0.0（20000）。
  - APK 内只剩两个 `nexus-node.sha256`，没有 Linux 程序，也没有 Python 脚本。
  - 原生库为 gojni、nexus_android、shoes。shoes 仍被订阅节点的 `ShoesEngine` 使用。
- 扫描本轮提交，只发现合成测试值，没有真实 IP、邀请或链接。README 引用的文档都存在。
- 没有复跑：覆盖升级和分享面板（雷电实例 1 上的测试）、正式签名，以及 GitHub CI。

### 结论

可以发布，没有需要修改的地方。

- V1 移除范围正确。按应用分流、出口查询对 V2 和订阅仍然可用，删掉的锁定、出口监测、自定义 DNS 等都是 V1 私人节点专属设置。
- 升级清理先提交偏好的删除，再删除 V1 密钥，失败时下次启动重试。V2 绑定和订阅都保留。
- 诊断导出只在用户点击时生成。机型按白名单识别，错误码只取 1–7，不含地址、密钥、链接或标识，与 PRIVACY.md 一致。
- CHANGELOG 和 README 的说法如实。性能注明是单线路实测，没有夸大。

### 发布顺序（每一步需用户确认）

1. 将 `v2/m0-transport` 快进合并到 `main`（`main` 是它的祖先）。
2. 推送 `main`，等 `build.yml` 第一次在 GitHub 上跑 V2 构建并通过。
3. 推送标签 `v2.0.0`，由 `release.yml` 正式签名并发布 APK 和节点程序。
4. 用正式包部署一次，确认服务器能从 GitHub Release 下载 `nexus-node`。
