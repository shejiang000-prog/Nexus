# 协议 V2 · M0 第一部分：传输层

开发分支从 main `1b2fa5e` 建立，规范分支基线为 `643e3d7`。本轮本地签入 Go 传输模块、Caddy 节点入口、补丁工具和 Android 合编回归入口。正式 API 见开发分支的 `docs/protocol/v2-transport-api.md`，站点对照详表见规范分支 `docs/protocol/v2-design.md` 的「M0 实测」。

## 改动

- `v2/proof`、`transport`、`udp` 实现 TLS exporter 连接绑定、一次签名、乐观 TCP 和两种 UDP 承载。选择器按第 6 轮保留首个静默窗口预建 H2、第二个窗口比较以及旧流收包判定。H2 将出站 HPACK 表限制为 1 字节，容不下任何证明项；本版 QPACK 编码器使用静态表和字面量。
- `v2/server` 和 `cmd/nexus-node` 处理已认证 CONNECT，将其他请求交给后续 Caddy handler。受信配置可按入口设置静态内存设备公钥；目的域名只解析一次，任一答案命中禁止段则拒绝，实际拨号使用通过检查的字面地址。实验室仅对回显服务的特定地址与端口临时放行。
- `tools/prepare_v2.py` 从 go.sum 校验上游模块、应用五份补丁并生成仓库外的 modfile。`tools/build_v2_aar.py` 将客户端与固定 libXray 绑定到同一个 Go 运行时。GitHub Actions 新增独立 Go job，沿用原有 Android job。许可证列入开发分支 `THIRD_PARTY_LICENSES.md`。
- `v2/internal/xconnect`、systemd 服务定义、Android Application、可选 Gradle 合编和 M0Check 完成 H2 初始化。上游 Go 1.27.4 的 `src/net/http/internal/http2/http2.go:50,59–60` 在 init 中读取环境并保存布尔值；`server.go:776–777,2128` 读取已保存的值。x/net v0.60.0 的 `http2/http2.go:62–63` 在包初始化时做同类处理，`transport.go:2568` 接收对端 SETTINGS。Go 节点在 main 发现环境不符合要求时保留其他项并重新执行一次，Android 在加载合编库之前调用 Os.setenv。[Go 源码](https://go.googlesource.com/go/+/refs/tags/go1.27.4/src/net/http/internal/http2/http2.go) · [x/net 源码](https://go.googlesource.com/net/+/refs/tags/v0.60.0/http2/http2.go)

## 留给下一轮

1. 对标准及 legacy Go 升级执行同一套握手、门槛回归。此轮验证了原型选择器移植和连接回显，没有重跑 100 次故障注入或重新比较 Chrome 握手分布。Android 本轮仅验 x86_64 合编、H2 UDP 和指定的三项 Xray 回归；arm64、真机 VPN、系统物理网络绑定和 release 尚待验收。
2. 固定互通向量已验证设备证明、邀请字节、跨连接失败、同连接并行和撤销后无法另开流。向量包含 0-RTT 和兑换事务的预期状态；真实 0-RTT 报文、邀请并行扣次及到期、存储故障和活动流撤销时限须专门验收。设备账本和邀请兑换服务归 M1。
3. 初始业务限制为每流 16 KiB。服务端完成验证及拨号才消费请求体；HTTP 栈预读的全连接 64 KiB / 2 秒上限尚无负载证据。签名回调在模拟器通过，StrongBox 尚未测量。systemd 单元未经系统安装；云端 Actions 未触发。
4. DATAGRAM 配置只解决一个监听上的 H3 能力宣告。进程级 H2 SETTINGS、QUIC 流控窗口仍可观察。三组顺序重启，未测同进程多监听热重载或大样本时序判别。

## Claude 评审

**结论：M0 第一部分通过，可以继续。** 结构清楚，安全边界正确，补丁流水线可复现。冻结接口前还有两处伪装差异和一个构建依赖要处理，见下面第 1–3 条。

**独立复现（NexusLab，离线，仅用已有模块缓存）。** 从 dec8684 的 `git archive` 重新运行 `prepare_v2.py`，五份补丁全部应用。默认标签和 `http2legacy` 两套 go vet 都通过。`-tags http2legacy` 下全部 10 个包 `go test -race` 通过，integration 1.13 s。**默认标签提供节点二进制后，`TestNode/h2` 失败**：`http: invalid header field name ":protocol"`，H3 子项通过。交接文档写的是默认标签那次「没有提供节点二进制」，所以这个失败没有暴露出来。

**代码审查确认没有问题的部分：**
- 证明格式、固定 115 字节检查、同连接只签一次、每次请求重新查设备（撤销后不能再开新流）。
- H3 拒绝 0-RTT；认证失败一律交给下一个 handler，探测者看到的仍是文件站点。
- 目的地址策略：先完整解析一次，任何一个结果命中保留段就拒绝，只拨已核验的字面地址。保留段覆盖云元数据地址（169.254/16、100.100.100.200、168.63.129.16、fd00:ec2::254）。
- `prepare_v2.py` 用 go.sum 的 h1 校验 zip，路径穿越检查到位，产物只写在仓库外。
- 测试向量使用私钥为 1 的合成密钥，并明确标注；扫描未发现密钥、节点地址或二进制文件。

**需要修正（按优先级）：**
1. **H2 设置项 8=1 是一个固定的可区分特征，而且它是 GODEBUG 方案带来的。** 原版 Caddy 的 H2 SETTINGS 没有 ENABLE_CONNECT_PROTOCOL。现在为了 H2 上的 RFC 9298 必须在进程级打开，同时还要求三样东西：服务端重新 exec、Android 在 Application 里全局 setenv（libXray 也会受影响）、客户端的 `http2legacy` 标签（也就是上面那个失败的原因）。建议 H2 上的 UDP 改用**普通 CONNECT**：authority 写目标地址，通过认证后才解析的请求头标记为 UDP，数据流里继续用 RFC 9297 capsule。这样能一次去掉 8=1、GODEBUG、重新 exec、Os.setenv 和 legacy 标签。H3 保留 RFC 9298，因为原版 Caddy 的 H3 本来就宣告 8=1。H2 的 RFC 9298 没有第三方客户端在用，不会损失互通性。
2. **QUIC 初始流控窗口和原版不同**（3145728/2097152 对 786432/524288）。Caddy 补丁里的 quic.Config 没有设置窗口，这两个值来自 apernet 分支的默认值。在 caddy-datagrams.patch 里显式设成上游 quic-go 的默认值即可，因为窗口会自动增长到上限。改完后要复测吞吐门槛，确认没有退步。
3. **H3 DATAGRAM（51=1 和 0x20）在同一个监听上无法消除。** 只能二选一：要么保留 DATAGRAM，UDP 性能更好；要么只用 capsule，看起来和原版 Caddy 完全一样。需要实测两种模式下 UDP 的时延和丢包，再决定默认值。无论选哪种，都要在设计文档里如实写明。（Hysteria2 在这一点上同样可见，所以这不是相对竞品的劣势，但也不能宣传成优势。）
4. **冻结前接口还缺两项：**
   - Android VPN 需要的套接字保护回调（`protect(fd)`），否则节点连接会回流进 TUN。这个回调现在就要进入 Go 和 JNI 签名。
   - Java 侧拿不到结构化错误码。
5. **乐观数据的错误码过于保守。** 只要收到了非 2xx 响应，服务端就没有把数据交给目标，应该返回对应的错误码。只有没有收到任何响应时，才应该是 7（结果未知）。
6. **只拨第一个地址。** 客户端 `dialQUIC` 和服务端 `target` 都只拨解析结果里的第一个地址，在 IPv6 不通的网络上会失败。核验过的地址应该依次尝试，或者用 Happy Eyeballs。
7. 小问题：
   - H2 预建每次都要调用一次 Keystore 签名，应限频。
   - 服务端未认证连接的拥塞控制是分支默认的 Reno，原版是 Cubic。
   - 客户端请求带 `quic-go HTTP/3` / Go 默认 UA，节点访问日志里能看到，建议去掉。
