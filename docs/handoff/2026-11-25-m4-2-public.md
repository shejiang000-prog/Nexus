## UDP 单向封锁

临时防火墙表仅在 VPS-A 的 input 链丢弃发往 V2 监听端口的 UDP。客户端在 SSH 规则命令返回时记录时间，并映射到 Android 单调时钟。热测结束后停 VPN、撤掉热测规则，再单独施加同一规则。冷启动也从这次规则命令返回计时，包含通知模拟器和启动 App VPN 的耗时。每个新 TCP 连接核对随机回声。按用户补充决定，WebView 每项只导航一次，经 VPS-A 的 VPN 打开 VPS-B 的公开 HTTPS 网站，校验 URL、主文档、9 字节正文和成功状态。主文档收到完整成功响应是网页门槛，和页面加载完成回调分别记录。表中单位为秒。

上轮从准备信号开始计时，旧请求超时不能证明 H3 已关闭。观测版在相同公开网络上复现了两种延迟。热切换中，多次 H2 拨号已成功，但 850 ms 内收不全 32 KiB 健康对象就被丢弃。直到 50.360 秒才选中 H2，51.196 秒收到新 TCP 回声，55.336 秒打开网页。冷启动在 1.181 秒选中 H2，1.613 秒 VPN 就绪，2.483 秒收到回声，2.061 秒至 3.021 秒有实际 DNS 往返，5.177 秒收到网页首字节，6.967 秒完成页面。上轮没有分段记录，无法逐毫秒还原那两个样本。

首次修复改用已认证的 HEAD 验证 H2，保留实际 H3 探测，放宽后台回探的握手与对象传输时间。Android 合并已缓存的 TCP 首段和首个 DNS 数据报，各自只发一次。三次初测的热切换回声为 4.877、11.233、4.939 秒，冷启动回声为 2.087、2.007、3.427 秒。单向封锁下仍有旧 QUIC 包抵达，已验证的 H2 会因原始收包计数增长被再次丢弃。改用业务下行和两次 H3 认证 HEAD 后，三次外站页面仍用时 12.487、8.404、7.729 秒（热）和 6.106、5.483、4.850 秒（冷）。三轮都曾在封锁前验证过可用 H2，这些连接随后被关闭，重新起拨时有网络超时。最终版将业务触发且已认证的 H2 短暂保留至多 5 秒，临切换再验证。

改用 VPS-B 的公开网站后，第一组 3 次均返回 HTTP 200 和正确的 9 字节正文。热切换主文档为 5.520、5.428、5.593 秒，冷启动为 3.164、3.450、2.768 秒。三次冷启动 H2 确认耗时分别为 0.436、0.420、0.413 秒。随后将首个 H3 认证探测提前到首个业务弱窗口，允许同一停滞阶段内等满 850 ms 且无响应头的认证 GET 作为第一次失败，保留两次探测的原有超时预算。Android 冷启动并行起拨 H2；H3 握手已有进展时保留优先窗口。

## 节点和真机准备

- VPS-A 为 Debian 13。App 绑定原节点并通过「更新节点程序」升级。升级前实际内核值已为 BBR 和 fq。升级后核实自有 sysctl 配置已落盘，唯一一次重启后两项设置仍是 BBR 和 fq，两项节点服务均已恢复。已核对两台节点的已安装程序与实际部署用 APK 内的 Linux 程序摘要相符。内核不支持时的回滚与保留管理员设置通过安装器测试。
- VPS-B 的实际系统为 Ubuntu 26.10，经补充批准加入矩阵。通过 App 使用对应 sslip.io 域名一键部署，75.6 秒进入管理页。V2、Reality、Hysteria2 的 systemd 服务均为 active。Ubuntu 26.04 通过安装器预检测试，本轮没有使用该版本的公网主机。
- VPS-A 在更新后交替下载同一 11,094,114 字节 HTTPS 文件，每次核对长度和 SHA-256。三次 Reality 为 4.52、3.81、4.06 Mbps，中位数 4.06。仅阻断 V2 入口 UDP 并确认 V2 使用 H2，三次为 7.24、4.97、2.19 Mbps，中位数 4.97。测速使用已合入 TCP 首段优化的 Android 包，早于最后的单向失效判定调整。
- VPS-A 保持 VPN 连接时重启一次。自客户端重启准备信号起，首次 HTTPS 失败为 4.263 秒，首次恢复为 71.330 秒；核对新系统启动标识后再次成功为 78.586 秒。同一 App 进程和 Android VPN 网络自动恢复，承载为 H3。
- SSH 仅 TCP 建连超时显示换 IP 的提示，鉴权等其他错误保留原行为。安装器针对性测试、Android 单元测试、Go 传输和路由回归、离线双架构构建通过。两台机器首次 SSH 信任按本轮授权执行，后续操作核对保存的主机密钥。
- 真机目录已更新独立 Debug APK 和四条新链接，真机由用户执行。

| 项目 | 结果 |
|---|---|
| 冷启动（门槛 3 秒） | 通过。新回声 1.68–1.72 秒，VPS-B 网页主文档 2.35–2.51 秒。 |

网页与隧道恢复之间多出的 1.3–1.9 秒，是经隧道访问目标站点所需的 TLS 握手和请求时间。任何代理都有这部分开销；不封锁时访问同一外站，到首字节也要 2.2 秒。我们可以压缩的是 H3 失效判定，公网上为 3.2–4.0 秒，实验室约 1.9 秒。慢样本中，850 ms 的 GET 无响应后，又串行等待了两次认证 HEAD。

**测速**：VPS-A 升级前已是 BBR + fq。上轮"未启用 BBR 导致 Reality 慢"的推断不成立，慢的原因是这条跨境 TCP 线路本身。安装器现在会确保启用 BBR。实测中位数如下：

| 协议 | 中位数 |
|---|---:|
| Reality | 4.06 Mbps |
| V2 强制 H2 | 4.97 Mbps |
| V2 H3（上轮） | 10.72 Mbps |

对外只能说"UDP 可用时明显快于 Reality；UDP 被封时与 Reality 相当"。各组测量的时段不同，且只测了这一条线路。

### 结论

冷启动、隧道恢复、回到 H3、部署、重启和提示都已达标。使用中被封后的网页恢复为 5–6.3 秒，超出约定门槛约 1 秒。是否接受由用户决定。如果接受，进入真机检查，判定速度留到发布后优化；如果不接受，再做一轮，只针对 H3 失效判定。
