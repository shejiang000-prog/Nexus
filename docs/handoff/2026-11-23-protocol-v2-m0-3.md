## 吞吐验收与中继实验

正式规则见规范第 7 节。每个工况预登记 60 对，按编号有放回重采样 10,000 次，每次重新计算两个中位数的相对差。20 Mbit/s、150 ms RTT、每方向丢包 0%/5%，Go 与官方 Hysteria 默认交替下载并校验 4 MiB。链路种子分别为 9207+2i、11207+2i（i=0…59），bootstrap 种子均为 4。全部 240 笔成功，没有补样。测试共用实验室主机，网络整形在独立命名空间内运行。

TCP 中继在每次 Write 成功后 flush。候选只把复制缓冲改为 64 KiB，可用数据不足一批时仍立即发出。0% 的差距仍在；旧版本的约 −1.1% 来自另一轮实验，无法据此把差距归因于 flush 或确认缓冲增大的收益。候选多占每条流约 32 KiB，因此恢复原实现。上表适用于实验候选。本轮没有抓取完整数据流的包长或在同轮额外比较两种缓冲。规范分支的 `docs/benchmarks/v2-m03-buffer64-loss{0,5}.csv` 保存配对速率，`tools/v2_throughput_gate.py --bootstrap-seed 4 <两份 CSV>` 可复算；`docs/benchmarks/v2-m03-hello-fields.csv` 保存 200 行握手字段摘要。

## M1 首批账本

显式授权后新增节点专用 modernc.org/sqlite v1.58.0 及其传递依赖。该版本由现有 Go 模块图选择，原有直接依赖版本保持一致。Windows 获取模块时启用了 Go 校验和数据库，WSL 从已有文件缓存复现。Android 库不包含服务端数据库代码。

- HTTPS POST 在本连接上验证 exporter、兑换 ID、公钥和邀请摘要的签名。SQLite 即时写事务同时扣唯一名额、登记设备、写审计；有效期内幂等重试只取回原 ID。
- 节点支持选择账本或原有内存设备表。跨进程撤销由已提交的审计序号驱动，登记流前再次检查设备状态。账本表结构和额度租约设计见开发分支的 `docs/protocol/v2-node-ledger.md`。
- 余额预留与结算、重启对账、备份、管理 CLI、到期主动断流及大负载撤销延迟留待后续。此轮测量覆盖实验节点上的活动流，尚不能给出生产负载最坏延迟。公开版 App、真实移动网络和真实 VPS 未参与。

## Claude 评审

**结论：M0 冻结接受，M1 第一批通过。** 账本有一个已复现的缺陷（第 1 条），下一轮必须先修。安卓端的握手指纹还没有验证（第 A 条）。

**独立复现（NexusLab 离线，11f7f39 的 `git archive`）。** 补丁准备、节点构建和 go vet 都通过；`go test -race -count=1 ./...` 全部 9 个包通过，包括 SQLite 账本、并发兑换和跨进程撤销。

**M0 部分**
- 接口冻结（607a3f8）接受。Resolver 回调、默认 Chrome 157 配置、变更记录和维护流程都写清楚了。生成器只提取签名算法和 ca34 两个公开字段，而且会核对锚的摘要，这种做法很稳妥。
- **A. 安卓合编库里的 uTLS 版本和桌面测试的不一样。** v2/go.mod 固定的是 v1.8.2，但 libXray v26.11.9 要求 `v1.8.3-0.20261108164504-a13c59ffe98b`，合编时 Go 会选更高的版本。这也解释了 M0Check 第一次运行时为什么出现「重复扩展」：两个版本的 `HelloChrome_Auto` 指向不同的预设。所以 50/50 只证明了桌面版本，安卓上实际发出的 ClientHello 还没有验证过。需要：
  1. 把 v2/go.mod 的 uTLS 对齐到 libXray 用的版本，重跑默认路径 50/50；
  2. `build_v2_aar.py` 检查合编后实际选中的 uTLS、apernet/quic-go、x/net 版本和 v2/go.mod 一致，不一致就构建失败；
  3. 从雷电向实验节点采样 H2、H3 各 50 次，和 Chrome 157 逐字段比对。
- **B. 冻结版代码还没有按新口径测过吞吐。** 本轮按 60 对规则测的是 64 KiB 缓冲的候选版本，之后又改回了原实现。另外，实施计划要求的格子是 1% 和 5% 丢包，对手是 Hysteria 和 TUIC 两个，而 TUIC 至今没有和正式代码比较过。这是发布前的门槛，下一轮按规范第 7 节补齐四格（1% / 5% × Hysteria / TUIC），每格 60 对。
- 0% 丢包下 −0.96% 的差距仍在。flush 的假设没有得到证实，Codex 没有把它算作结论，这个处理是对的。这个差距在门槛内，暂时搁置。

**M1 账本**

做得对的地方：
- 只保存邀请摘要，不存原令牌；
- `BEGIN IMMEDIATE` 保证并发兑换只扣一次名额；
- 兑换失败交给站点，而且凭据正文会被清空；
- 撤销会关闭整条连接（一条连接只绑定一台设备，所以是对的）；
- 登记流之前会再查一次数据库，堵住了认证和登记之间的空档；
- 审计记录和业务写在同一个事务里；
- 数据库文件必须是 0600；
- 撤销实测 108 / 112 ms。

需要修正：
1. **已复现：数据库被别人短暂锁住，就会断开所有用户。** `watchRevocations` 查询出任何错误（含 250 ms 超时）都会调用 `disconnectAll`。数据库没有开 WAL，所以其他进程一旦持有排他锁，读也会被挡住。我写了临时测试：另开一个句柄 `BEGIN EXCLUSIVE` 并保持 600 ms，结果未被撤销的设备的活动流被关闭了（`stopped: true`）。备份、管理工具或 sqlite3 命令行都可能触发。
   - 修法：开启 WAL；监视查询失败时只重试，不断开。
   - 理由：撤销必须提交以后才生效，而提交本身需要拿到写锁，所以「读不到」不会让一个已提交的撤销被长时间隐藏。持续失败（例如文件被删、数据库损坏）时记日志，超过较长阈值再按故障处理。
   - 请把我上面这个测试改成正式回归测试。
2. **兑换接口可以被用来制造锁争用。** 攻击者用自己生成的密钥，就能对任意令牌做出合法签名，然后每个请求都会开一个 `BEGIN IMMEDIATE` 写事务。结果是正常用户的 Lookup 变慢或失败，被当成未认证请求交给站点。修法：先只读查询邀请是否存在且有效，命中后才开写事务；同时对兑换路径按来源地址限速（超限按失败处理，同样交给站点）。
3. **每开一条流都要查数据库，而且查询期间持有全局锁。** `Accept` 和 `register` 都调用 Lookup，`register` 查询时还持有 `l.mu`。数据库只有一个连接，所以全节点的开流请求是排队进行的；数据库一忙，正常用户就会被悄悄当成网站访客。建议：
   - 设备状态放进内存缓存，由兑换、撤销和监视器更新；
   - 不要在持锁时查库；
   - 加负载测试：50 台设备并发开流，同时穿插兑换和撤销，报告开流 P99 时延和误判次数。
4. **账户到期不会断开活动流。** 规范要求撤销在 1 秒内生效，到期应同样处理：监视器同时检查到期时间。
5. 节点还没有管理入口：创建用户、生成邀请、列出设备、撤销都还没有。管理工具必须走 Ledger 接口，以保证写审计。
