# PC-M2 · Windows TUN

基线 `fba8c5b`，本地开发分支 `v2/m0-transport`。Windows x64 验收目录为 `E:\代理软件\验收包\PC-M2`。桌面程序、配对的核心和权限助手、原版 `wintun.dll` 及三份许可须一起使用。发布时应安装在普通用户不可写的本地目录，例如 Program Files。正式安装包和程序签名沿用后续发布计划。

## 连接与恢复

- 首页「TUN 模式」每次启动默认关闭，与「系统代理」独立。选择已登记的 NexusLab 身份或兼容订阅节点，开启 TUN 后点连接才请求 UAC。普通连接无需提权。界面有权限、驱动、冲突、数据通道中断及恢复失败的独立中文提示。
- 同一个普通权限 `nexus-core.exe` 运行固定版 Xray 的 TUN 入站和 M1 的 `selected` 出站。TCP/UDP 均按原有全局或绕过大陆规则分发。TUN 中的 TCP/UDP 53 按每个 DNS 问题分流，国内查询使用当前物理网卡的解析器，其余经所选节点。分流模式按 DNS 答案的 TTL 记住国内域名的地址，换网时清空。节点域名的引导解析及连接固定走物理出口，节点使用 IP 时省去引导解析。
- 助手仅提供三种固定操作：整机、TEST-NET、遗留恢复。普通核心锁定助手摘要，助手锁定官方 DLL 摘要。随机 256 位本机命名管道核对进程、登录 SID、终端会话及同目录核心路径。传输内容仅有状态字节和有界 IP 包。请使用同一登录用户的 UAC 分离令牌。输入另一账号的管理员凭据会被拒绝。
- 助手创建随机 GUID 的 Wintun 网卡，先将用户、进程创建时间、接口 GUID/LUID 和操作意图写入受保护的 64 位 `HKLM\SOFTWARE\NexusDesktopTun\Session`。地址、路由和 DNS 设置均属于新网卡。停止、窗口退出、核心或父进程异常退出时回收该设备。助手也崩溃时，下次启动先核对记录及设备身份，必要时单独请求恢复权限；未成功清理时保留记录。驱动可由其他程序共享，保留 DriverStore 中的驱动包。
- 整机模式使用 IPv4/IPv6 各两条半默认路由覆盖公网，网卡切换时重新选择物理出口、更新解析器路由并退役旧连接。短暂无默认路由时，已建立的会话保留接管与 DNS 保护并等待新链路。发现竞争路由或无法安全接管的解析器时连接失败。
- 整机模式还通过 Windows Filtering Platform 的动态会话阻断绕过 TUN 的普通 TCP/UDP 53。对支持加密系统 DNS 的 Windows，限制 DNS Client 服务的物理出口，同时保留指定的本地组播名称发现。规则随权限助手进程退出而撤销；没有持久 Defender 防火墙规则。为物理 DNS 放行的程序按固定核心路径识别，同路径的核心实例具有同一应用标识。第三方应用自带的 DoH 按常规数据流参与分流，无法按加密内容判断问名。
- 测试路由模式仅在新网卡配置 `192.0.2.1/32` 和三条 IPv4 路由：`192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`。保留系统 DNS、默认路由和防火墙；测试网段的数据强制走所选节点，DNS 仍按问名分流。该模式仅从本地测试命令进入。

## Claude 验收（五步）

1. 征得用户同意后，在可提权的隔离 Windows 上使用受保护的本地安装目录。记录 `Get-NetAdapter -IncludeHidden`、`Get-NetRoute`、`Get-DnsClientServerAddress` 和 WinINet 当前代理。关闭 Nexus 的「系统代理」。准备**仅供 NexusLab 使用**的 V2 身份和合成订阅，入口应可由物理网卡或受控回环中继到达。可在实验节点内用 `203.0.113.10` 提供 HTTP/TCP 回显 `:18080`、UDP 回显 `:18081` 及合成权威 DNS `:53`；实验的 `allow_exact` 仅放行相应地址和端口。不要连接生产节点。
2. 普通权限启动 `nexus-core.exe`，通过保持打开的匿名 stdin 写一行 `{"action":"start_test_tun","invite":"","mode":"global"}`（使用已登记实验身份），同意该会话的一次 UAC。订阅用 `{"action":"start_test_tun","source":"subscription","subscriptionId":"<本地来源ID>","nodeId":"<本地节点ID>","mode":"split"}`。等待 `ready:`；核对新增接口仅承载上述测试前缀，系统 DNS 和原默认路由与基线一致。不要用一次性管道写入命令后立即关闭 stdin，EOF 即断开。
3. 每种来源各做一轮。通过 `curl.exe --noproxy "*"` 访问上述 HTTP 回显，用未设代理的 UDP socket 收回随机短串，用 `Resolve-DnsName <随机>.invalid. -Type A -Server 203.0.113.10 -DnsOnly` 查询实验 DNS，再加 `-TcpOnly` 检查 TCP DNS。核对实验返回值及节点收到的请求。在实验物理解析器查国内问名，核对只有该解析器收到查询。
4. 先正常关闭 stdin，等待核心、助手退出。再用测试路由重连，分别模拟核心异常退出和助手异常终止，只终止本次已核对 PID 的进程。重新打开桌面程序并允许恢复，核对自有 GUID 网卡、测试路由及 `Session` 值已清除，其他网卡、DNS、代理和路由与基线一致。
5. **另行征得用户对整机接管、临时 DNS 过滤及切网的明确同意**，再用首页 TUN 开关验证。对 V2 与订阅分别检查国内及境外 DNS、IPv4/IPv6 TCP 与 UDP，以及 Wi-Fi/有线交替期间的通路和 DNS 去向。核对物理网卡只出现预期的节点通信、引导及国内 DNS。若另获 WinINet 验收许可，可同时开启系统代理；否则保持关闭。断开或退出后重做基线比对，确认自有网卡、路由和动态 DNS 过滤均已撤销。

## Claude 评审

结论：**代码层面通过**。真实网卡、路由和防泄漏规则还没有在管理员权限下跑过，PC 版发布前必须完成本交接的五步验收。

复现：
- `--test-routing --test-tun` 下 `nexus-core`、`nexus-tun-helper` 和 `dnsguard` 测试全部通过，`cargo test` 和 `cargo build` 也通过。
- Wintun ZIP 的 SHA-256 `07c25618…24ef51` 和 DLL 的 `e5da8447…dafce` 与 DEPENDENCIES.md 一致。DLL 的 Authenticode 签名采信交接中的 signtool 结果，我没有另行核对。

设计检查：
- 权限分离是对的：普通权限的核心跑 Xray，提权助手只持有 Wintun 会话、路由和 WFP。助手只接受三种固定模式。连接方校验了管道服务端 PID、终端会话、用户、登录 SID（包括 UAC 关联令牌）和同目录核心文件身份。回送的包只能发往本会话网卡的地址，核心无法借助助手向任意地址注入数据包。
- 提权前，核心锁定助手文件摘要并逐级拒绝重解析点；助手加载 DLL 前也锁定摘要。
- 恢复以 HKLM 会话记录为准，按接口 GUID/LUID 核对所有权；WFP 只用动态会话，进程退出即撤销，不留持久防火墙规则。

需要在验收中确认或后续处理：
1. **吞吐量**：所有 TUN 数据包都经命名管道在助手和核心之间逐包转发。这种结构比 v2rayN、Clash 让核心直接持有 TUN 多一次跨进程拷贝。验收时要测下载速度和 CPU 占用，与「系统代理」模式对比；如果明显偏低，再改为批量帧或共享内存环。
2. **每次连接都要 UAC**：每次开启 TUN 都会弹一次授权确认，日常使用比较烦。M3 做安装包时可以考虑：安装时注册一个只接受同样固定操作的系统服务，连接时就不用再提权（Clash Verge 的「服务模式」也是这样做的）。
3. 测试路由模式只覆盖 IPv4；整机模式的 IPv6 和切网只能在第 5 步验收里验证。
