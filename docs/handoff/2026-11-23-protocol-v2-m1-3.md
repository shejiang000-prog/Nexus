## 运行时与构建

用户的所有设备共享一份至多 8 MiB 的租约。TCP 部分写按返回字节计入，UDP 完整包按有效载荷计入。6 个并发写入者的测试实际写出 491,521 字节，与配置额度一致。H2 和 H3 独立节点用例让两台设备的 TCP 和 UDP 竞争同一限额，并验证耗尽及跨进程置零后的断流与新流准入。

原先每条短流结束都同步结算，50 设备回归让 SQLite 写锁竞争导致撤销返回 SQLITE_BUSY。现在流结束按用户在 25 ms 窗口内合并结算。另在 Caddy 开始停机时关闭账本业务，避免在默认无限宽限期内等待永久 CONNECT。

AAR 用一次 gomobile bind 合编 android/arm64 和 android/amd64，逐个检查原生库依赖版本、替换路径和校验和。移除 8 个已替换版本的 16 条旧校验记录。清理后的离线 prepare、双 ABI 合编和 Debug 测试包构建均通过。arm64 用静态检查验收。

## 恢复演练

独立节点保持 TCP 活动流，用户额度 1,048,576 字节。发送 4 字节并读回回显，周期结算为 8 字节。再发送并读回 1 字节，此时活动租约仍包含 2 字节未结算用量。

|场景|观察结果|
|---|---|
|SIGKILL 后从原库重启|活动租约转为 frozen，已用量按 1,048,576 字节显示。对账后已用 8 字节，再次对账没有新增流水。|
|带活动流在线备份、停机、换库、重启|副本保留 active 租约和 8 字节检查点。源库正常关闭时结算为 10 字节。移开旧库及其 SQLite 附属文件、换入副本后，恢复到备份点并按全额冻结。|
|恢复核对|用户、额度、设备和备份点之前的审计一致，冻结及对账后共 8 条连续审计。旧邀请无法用新密钥兑换。原设备能使用释放的余额继续回显。|

**缺陷 1（重要）：一条卡住的流会冻结同一用户的全部流量**

`quotaAccount.write` 在持有 `a.mu` 读锁期间执行实际的 socket 写；`ensure` 续租和用满后的最终结算需要 `a.mu` 写锁。只要某条流的写被对端流控卡住（例如客户端暂停视频、接收窗口满），同一用户的其他流在跨过 8 MiB 租约边界时就要等写锁。而写锁排队后，新的读锁也会被挡住，于是该用户所有设备的所有流都停下，直到那条卡住的写恢复，或者连接超时。

评审用例 `TestReviewStalledWriterFreezesUser`（不限额用户）：
- 一个 1 字节写阻塞后，另一流写 9 MiB 跨边界，3 s 后仍阻塞；
- 第三条新流的 100 字节写也阻塞；
- 释放第一条写后，跨边界流在 3.70 s 完成。

不限额用户同样受影响，因为不限额用户也按 8 MiB 续租。现有测试没有覆盖“写阻塞期间续租”。

修复方向：socket 写期间不持有租约锁。把租约做成独立对象（含 left、written 和引用计数）。写入者用 CAS 从当前租约扣预算，并持有该租约对象的引用，然后释放锁再写，写完把实际字节记到它所属的那份租约上。续租只替换“当前租约”指针。旧租约在引用归零时按实际 written 做最终结算，不需要等在途写完成。固定额度下超用上界为 0 的性质要保持。

**缺陷 2（中）：启用账本后 Caddy 配置重载必然失败**

评审用例 `TestReviewReloadWithLedger` 用 `--watch` 触发重载，与 `caddy reload` 走同一条路径。新配置在 Provision 阶段报 `cannot acquire node ledger ownership: database is locked`，Caddy 保留旧配置继续服务。已有流和新设备都正常，不会出事故。但任何配置修改都只能整进程重启，所有在线用户会断开，同时所有活动租约被冻结，需要 reconcile。日志里还有 `cleanup: sql: connection is already closed`：Provision 失败时已关闭账本，Cleanup 又关闭了一次。

修复方向：同一进程内按账本真实路径做引用计数，新旧 handler 共享同一个 Ledger 和所有者锁，最后一个引用释放时才关闭。重载不冻结租约，也不断流。如果本阶段不修，就须在账本文档和 M2 安装器中写明“启用账本后只能重启，不能 reload”。
